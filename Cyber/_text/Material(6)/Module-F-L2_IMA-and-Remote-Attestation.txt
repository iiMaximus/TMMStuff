  What problem does Remote Attestation solve?
   In distributed systems, trust is remote.
   A service may need to know:
   ➢ Is this node genuine?
   ➢ Did it boot with expected firmware and kernel?
   ➢ Is Secure Boot enabled and correctly
       configured?
   ➢ Are runtime components still trusted?
   ➢ Has the platform been tampered with?
   Remote Attestation provides:
   ➢ cryptographic evidence of platform state
   ➢ freshness against replay attacks
   ➢ binding to a hardware or firmware trust anchor
   ➢ policy-based trust decisions
   ➢ support for Zero-Trust architectures

  RATS conceptual messages (I)
   ➢ Evidence: claims about the Attester’s identity and integrity state
             •     For example, it may include information about which software is running, which
                   firmware was loaded, which configuration is active, or which hardware root of
                   trust is being used.
   ➢ Endorsements: statements (e.g., certificates) supporting the authenticity of
        attestation keys or trust anchors
             •     They help answer the question: “Is this really a valid attestation-capable
                   platform?”
   ➢ Reference Values: known-good or acceptable measurements
             •     They help answer the question: “Is the state reported by the Attester the state
                   that I expected?”
             •     For example, if the Evidence contains a firmware hash, the Reference Value
                   tells the Verifier which firmware hashes are acceptable (e.g., Accepted
                   bootloader hash: A1B2C3, Accepted kernel hash: D4E5F6, …)
Cybersecurity and National Defence (Grandi Sfide - Digital)
                                                                                                     8
A.Y. 2025 - 2026
  RATS conceptual messages (II)
   ➢ Appraisal Policy: rules used by the Verifier to interpret the Evidence
             •     The policy defines what should be accepted, what should be rejected, and
                   possibly what should be treated as a warning or degraded state
             •     For example: Accept the device only if:
                    o the bootloader hash matches an accepted Reference Value;
                    o the kernel hash matches an accepted Reference Value;
                    o Secure Boot is enabled;
                    o debug mode is disabled.
             •     the Appraisal Policy answers questions like: “Is a mismatch fatal, or only a
                   warning?”, “Can an old firmware version still be accepted?”, “Should the device
                   be denied if debug mode is enabled?”, “Is Secure Boot mandatory for this
                   device?”, …
   ➢ Attestation Results: verifier output consumed by a Relying Party, which uses
        them to make decisions, e.g., granting access, denying access, or applying
        some restriction

  TPM-based integrity challenge protocol
   Protocol steps:
   1. Verifier sends an integrity challenge with a nonce (to ensure freshness of the
       response)
   2. Attestation Agent requests a TPM quote, specifying to the TPM the received
       nonce, the AK to be used and the list of PCRs to be signed
   3. TPM signs selected PCRs with the AK, and returns the obtained signature
   4. Attestation Agent reads selected PCR values
   5. Attestation Agent retrieves measurement logs
   6. Attestation Agent sends to the Verifier the collected Integrity Evidence,
       which contains:
             •     TPM quote
             •     PCR values signed with the quote
             •     Measurement logs
            •      AK certificate

  How does a Privacy CA certify an AK?
   Goal: Certify that an AK is resident in the same TPM as the EK representing a
   genuine TPM, so that the AK can be used as an identity alias for the TPM.
   Simplified protocol:
   1.     Attester sends to the Privacy CA:
             •   AK public key
             •   EK certificate
   2.     Privacy CA verifies the EK certificate, making sure it was issued by trusted TPM
          manufacturers
   3.     Privacy CA creates a secret challenge encrypted with the 𝐸𝐾𝑝𝑢𝑏 and bound to the AK
   4.     TPM runs ActivateCredential and recovers the secret only if:
             •     it owns the EK private key
             •     the AK is loaded/resident in the same TPM
   5.     Privacy CA receives the secret back and issues an AK certificate

            The Privacy CA certifies the AK is resident in a genuine TPM, so future
           quotes can be verified using the AK certificate instead of exposing the EK.     16

  Why the quote alone is not enough
   In TPM 2.0, the quote is the TPM-produced signature over attestation data.
   ➢ It authenticates selected PCR state and binds it to the nonce sent by the
      Verifier. This gives authenticity and freshness.
   ➢ The Verifier also needs the selected raw PCR values, retrieved separately,
      e.g., with: TPM2_PCR_Read
   ➢ But PCR values are only aggregates, they could be not enough to understand
      the platform state:
       𝑃𝐶𝑅𝑓𝑖𝑛𝑎𝑙 = 𝐻𝑎𝑠ℎ(… 𝐻𝑎𝑠ℎ 𝐻𝑎𝑠ℎ 𝑃𝐶𝑅𝑖𝑛𝑖𝑡𝑖𝑎𝑙 ∥ 𝑀1 ∥ 𝑀2 … ∥ 𝑀𝑛)
   ➢ So the Verifier also needs the measurement log, containing the detailed
        history of measurement events, to know:
             •     what was measured; in which order measurements were extended;
             •     which component generated each measurement; which component caused a
                   mismatch; whether each event is acceptable under policy.

A.Y. 2025 - 2026
  Step 1: Authenticate the Attestation Key
   Goal: The Verifier checks whether the quote-signing key is a legitimate attestation
   key from the attesting platform, not an arbitrary software-generated key.
   Checks may include:
   ➢ Does this AK certificate identify the platform I want to attest?
   ➢ Was the AK certified as TPM-resident?
   ➢ Is the certificate-chain trusted? That is:
             •     do I trust the Privacy CA (or Attestation CA) that issued the AK certificate?
             •     do I trust the Root CA that certified the Privacy CA, and so on?
             •     or (if I’m not using the Privacy CA), do I trust the EK certificate and the TPM
                   manufacturer?
   ➢ Is the AK certificate still valid or has it been revoked?
   Why this matters:
   Without AK authentication, any software key could sign fake evidence, or any
   platform can impersonate the attesting platform.
Cybersecurity and National Defence (Grandi Sfide - Digital)
                                                                                                     23
A.Y. 2025 - 2026
  Step 2: Verify the quote
   The Verifier checks:

   1. Signature
        •  quote signed by the trusted AK (verified at the previous step)
   2. Freshness
        •  nonce in quote matches the nonce sent in the challenge
   3. PCR selection
        • quote covers the PCRs required by policy (e.g., boot PCRs, runtime
          PCRs, …)
   4. PCR values
        •  received PCR values match the quoted PCR state

   If any check fails: reject the Evidence.
Cybersecurity and National Defence (Grandi Sfide - Digital)
                                                                               24
A.Y. 2025 - 2026
  Step 3: Validate the measurement logs
   The measurement log is outside the TPM, in system memory. Therefore, the
   Verifier must check that it has not been tampered with, so that it matches the
   TPM-protected PCR values.
   Verifier replay:
   𝑃𝐶𝑅𝑟𝑒𝑐𝑜𝑚𝑝𝑢𝑡𝑒𝑑 = 𝐸𝑥𝑡𝑒𝑛𝑑(𝐸𝑥𝑡𝑒𝑛𝑑 𝐸𝑥𝑡𝑒𝑛𝑑 𝑃𝐶𝑅𝑖𝑛𝑖𝑡𝑖𝑎𝑙 ∥ 𝑀1 ∥ 𝑀2 … ∥ 𝑀𝑛)

   Then compare:
   𝑃𝐶𝑅𝑟𝑒𝑐𝑜𝑚𝑝𝑢𝑡𝑒𝑑 == 𝑃𝐶𝑅𝑞𝑢𝑜𝑡𝑒𝑑
   ➢ If values match: log is consistent with the quoted PCR, so it is authentic and
     can be used for appraisal.
   ➢ If values do not match: log was modified, truncated, reordered, or does not
     correspond to the quoted TPM state. ⟹ In this case, the Evidence must be
     rejected.

  Step 4: Appraise measurements against policy
   After log validation, the Verifier checks individual measurement events.

   Reference Values answer:
   ➢ Is this firmware measurement known-good?
   ➢ Is this bootloader approved?
   ➢ Is this kernel version acceptable?
   ➢ Is this configuration expected?
   Appraisal Policy answers:
   ➢ Which PCRs/logs are mandatory?
   ➢ Which components are allowed?
   ➢ Are unknown components rejected?
   ➢ Are debug/test modes acceptable?
   ➢ What action follows a failure?

  Step 5: Produce the Attestation Result
   The Verifier produces an Attestation Result for the Relying Party.
   The result may include:
   ➢ trust decision: trusted / untrusted
   ➢ validated claims
   ➢ reason for failure (e.g., unknown component detected, or component with known
     vulnerability detected)
   ➢ timestamp / freshness context
   ➢ policy used
   ➢ recommended action
   Example decisions:
   o If trusted: allow access / deploy workload / release secret
   o If untrusted: deny connection / quarantine node, trigger remediation (e.g., update
        vulnerable components, remove / redeploy workload, restart node to restore trusted
        state, isolate the node and perform in-depth analysis)

  Limitation: boot-time trust is not runtime trust
   Question:
   If a machine booted correctly at 09:00, can we still trust it at 14:00?

   A platform may boot in an expected state, but later:
   ➢ execute malicious binaries
   ➢ load unexpected libraries
   ➢ load kernel untrusted modules
   ➢ run altered scripts
   ➢ use modified configuration files
   ➢ start unapproved services


                              Trusted Boot verifies how the system started.
                           It does not fully describe what happens after boot.

  Verifier-side validation of the IMA log
   The IMA log is outside the TPM, so the Verifier must validate it.

   Validation procedure:
   1. receive quoted PCR 10 value
   2. receive IMA Measurement Log
   3. start from PCR initial value (typically all zeros)
   4. Replay extend operation on all IMA log entries in order
   5. recompute PCR 10
   6. compare recomputed PCR 10 with quoted PCR 10

                             𝑃𝐶𝑅10 𝑟𝑒𝑐𝑜𝑚𝑝𝑢𝑡𝑒𝑑 == 𝑃𝐶𝑅10 𝑞𝑢𝑜𝑡𝑒𝑑
   If equal: log is authentic, consistent with TPM state.
   If different: log may be modified, truncated, reordered, or incomplete.
